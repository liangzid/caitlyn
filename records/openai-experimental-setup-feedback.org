* 结论

当前 =records/caitlyn-experiment-design.org= 的实验框架方向是够的，已经覆盖
主表、emerging benchmark、System II evolution、ablation、case study、成本、
adaptive attack 与长期演化。

但如果要让论文实验更稳，最建议补三类实验。优先级如下：

1. Detection-only sweep
2. Delivery-aware end-to-end table
3. System II evolution before/after on held-out variants

如果只能新增一个实验，优先选择 detection-only sweep。若要支撑 CAITLYN 的
核心 novelty，则 System II evolution before/after 必须做。

* E1: Detection-Only Sweep

** 目的

单独评估 CAITLYN 作为 detector 的能力，避免 end-to-end agent 实验中混入
agent 行为、MCP 投递、工具调用稳定性等噪声。

** 实验设置

输入为攻击样本与 benign 样本，不运行完整 agent，只调用防御检测器。

候选数据源：

1. AgentDojo subset
2. ASPI subset
3. SafeClawBench subset
4. AgentDefense-Bench detection subset
5. natural20

比较对象：

1. regex_guard
2. llm_judge
3. llm_judge_fewshot
4. CAITLYN

指标：

1. Detection rate 或 TPR
2. FPR
3. TPR at fixed FPR
4. AUROC 或 AUPRC，若防御输出可用连续分数
5. p50 / p95 latency
6. token 与 dollar cost

** 为什么重要

该实验回答一个基础问题：CAITLYN 本身是否比简单 regex 或 LLM judge 更适合作为
agent 防御检测层。这个实验便宜、规模大、噪声小，适合放在主实验中。

** 当前工程基础

最新代码已经包含：

1. =AgentEval/run_detection_sweep.py=
2. =AgentEval/src/agent_eval/security/dataset_adapters.py=
3. =valsets/eval_subsets/*=

因此该实验不是额外发明，而是把现有能力正式纳入论文实验设计。

* E2: Delivery-Aware End-to-End Table

** 目的

让 end-to-end ASR 的统计口径更可信。否则 ASR 降低可能来自攻击没有投递成功，
而不一定来自防御有效。

** 建议报告指标

主表中除 ASR 外，建议拆出以下指标：

1. Delivery rate: 攻击内容是否真实到达 agent context
2. Defense block rate: 防御是否拦截攻击内容
3. Action ASR: agent 是否真的执行攻击动作
4. Benign task success: 良性任务是否完成
5. Latency and token cost

** 关键口径

需要区分两类 agent 设置：

1. MCP-native delivery
2. Prompt-delivery fallback

不同 agent 的工具通道稳定性不同，不能把 delivery failure 与 defense success 混在
一起解释。

* E3: System II Evolution Before/After

** 目的

证明 CAITLYN 不只是 hybrid scanner，而是真的具备自适应防御能力。

** 实验设置

对每类 emerging pattern：

1. 选取 k 条 seed 样本进入 System II
2. held-out variants 不进入 generator、similar-sample retrieval、redteam context
3. 比较 evolution 前后在 held-out 上的表现

推荐变量：

1. seed k = 1, 3, 5
2. CAITLYN-static vs CAITLYN+evolution
3. optional: train on pattern A, test on related pattern B

指标：

1. held-out detection rate 或 action ASR
2. benign FPR
3. evolution rounds
4. evolution token cost
5. wall-clock time
6. accepted / rejected candidate counts

** 为什么重要

这是支撑 lifelong / adaptive defense 主张的核心实验。没有这个实验，CAITLYN 容易
被理解为一个静态多层扫描器，而不是会进化的防御系统。

* 关于 Hard Benign

此前讨论过 hard benign FPR，但不建议把自建 HardBenign-50 作为主实验。

原因：

1. 手工构造 benign 样本容易显得主观
2. reviewer 可能质疑 cherry-picking
3. 当前公开 benign 与 AgentDefense-Bench benign 已经能支持普通 FPR

若确实需要回应 keyword blocker 质疑，建议只做轻量补充分析：

1. 从公开 benign 数据中自动筛选包含 injection-like 表面词的样本
2. 单独报告该 slice 上的 FPR
3. 不把它包装为新的 benchmark contribution

示例筛选词：

1. curl
2. bash
3. execute
4. system
5. ignore
6. IMPORTANT
7. WARNING
8. email
9. forward

该实验可放 appendix 或 supplementary，不建议替代主实验。

* 最小推荐实验组合

若资源有限，建议保留以下组合：

1. End-to-end main table, using delivery-aware metrics
2. Detection-only sweep
3. System II evolution before/after on held-out variants
4. Cost analysis
5. One real case study trace

其中前三项是最关键的。

* 下一步建议

建议先把 =records/caitlyn-experiment-design.org= 中的主实验结构更新为：

1. Main end-to-end evaluation
2. Detection-only evaluation
3. Emerging benchmark zero-shot evaluation
4. System II evolution before/after
5. Ablation and cost
6. Case study

Adaptive attack、poisoning-resistance、long-term evolution 可以作为 appendix 或第二阶段
实验，避免主线过重。
